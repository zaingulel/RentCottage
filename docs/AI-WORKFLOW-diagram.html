One session, nine seats, two decisions

How a loose idea becomes cards on the board, and a card becomes a merged commit. The owner decides what to build and whether the finished change may ship. Everything between those two yeses is done by agents inside one worktree, checked by hooks and tests they cannot skip, and recorded in git and on the board rather than in chat. Every box below traces to a file in the repository.

Before the board: idea to cards

Three skills, run in an ordinary chat, turn a loose idea into work the build loop can pick up. None of them writes code.

  1. agrill-me, or wayfinder. The grilling skill interviews the owner in rounds, each round asking every question whose prerequisites are settled and giving a recommended answer, until the design tree is fully agreed. Work too big for one session goes to wayfinder instead, which charts investigation tickets on the tracker and resolves them one at a time until the route is clear.
  2. bto-spec. No interview: it synthesises what the conversation already settled into a spec (a PRD). It proposes the seams the feature will be tested at, checks them with the owner, and publishes the spec to the tracker as an issue.
  3. cto-issues. This repository's replacement for the upstream to-tickets. It breaks the spec into tracer-bullet vertical slices that cut through every layer, each sized to one builder handoff, each declaring what blocks it and which build seat it needs. The owner sees the numbered breakdown and approves it before a single issue is created. Slices are then published in dependency order, carded in Backlog with a Workstream, and linked to their Epic as native sub-issues.
  4. dThe board. Backlog holds everything not yet startable. The owner promotes a card to Ready when no owner decision, external dependency or scheduled date is missing. Resume, the first station below, reads Ready first.

The eleven stations, with their owners

Each station is a section of the resume skill, except the last, which is the closeout skill. The skill owns the exact commands; the manual AGENTS.md owns the rules.

  1. 1Resume. Fetch origin/main and advance the local main only when the fast-forward is provably safe; a dirty, active or divergent checkout is preserved and reported. Then read the board, the open draft pull requests (their "Not done" section is the handoff), and any issues the triage routine filed.
  2. G1Work-pick, owner gate one. A candidate table: outcome for the user, why now and the risk, the gates the card triggers, the build route and why. One row is recommended. The owner's pick of a row approves that card's outcome and acceptance criteria as written and starts the job, with no criteria list and no second yes; owner-directed surfaces need canon validation, sign-off surfaces need explicit sign-off and a named anti-regression test.
  3. 2Start the job. One git worktree on job/<issue>, cut from the recorded origin/main, with the session started inside it. The root checkout stays on main and is never edited. Two issues never share a working file; two slices of one issue with disjoint files can run in two worktrees cut from the job branch.
  4. 3Plan. Plan-first surfaces, the plan-first row of the Surfaces table in AGENTS.md, get an architect plan and one read-only plan-reviewer pass before any build; any other card with a design choice still open after work-pick gets an architect plan. A plan states its size envelope. Anything that changes the approved outcome goes back to the owner as a decision before it is built.
  5. 4Build. Every edit goes to a builder seat through the handoff template; the session never builds. Every executed check is wrapped in scripts/run-log.mjs so the pull request body quotes exit codes a script wrote. Each green slice is committed on the job branch. After two repair rounds that still produce true findings, the work is replanned or split.
  6. 5Verify. Visual work is driven as the Conventions table's visual verification row says and a current screenshot is shown in chat; any further gate the Surfaces table names runs here.
  7. 6Review. One fresh review of the final tree: the reviewer seat, run by the model family that did not write the diff, for code and agent instruction; the session itself for documentation and a setting-only seat change; the security reviewer only when the trust perimeter widens. True findings are fixed, false ones dismissed with a reason, then one pass scoped to the repaired hunks.
  8. G2Push authorisation, owner gate two. The filled pull request template and the screenshot. One yes, or any instruction to push, covers the push, the draft, the review comments, repairs, the rebase, marking ready, the queued merge and the closeout. Nothing inside delivery asks again.
  9. 7Deliver. Rebase onto origin/main, regenerate any generated artifact if needed, push, open a draft pull request whose body says Closes #issue. Card to In review.
  10. 8External review. Only the sign-off tier takes this step. Greptile is requested once by comment for the exact head; automatic reviews are disabled in .greptile/config.json. Every finding is fixed, set aside by the owner, or dismissed with evidence before the draft is marked ready. Every other change skips this step.
  11. 9Ready, then CI. gh pr ready starts CI, which runs the suites docs/TESTING-STRATEGY.md names, on the merge result rather than the branch head. On a draft the required check reports under a different name so it can never satisfy branch protection early.
  12. 10Auto-merge. The merge is queued as a GitHub auto-merge with squash and branch deletion. No agent merges directly; the git guard refuses any other merge form.
  13. 11Closeout. Confirm the merge, confirm the issues the body named are closed, advance local main, move cards to Done, run the drift check, delete the branch and the worktree. Rulings the owner made during the session go to the issue or the manual that owns the topic, never to a new document.

The standards layer

Four documents set the bar. They are not a step in the flow; they are what a seat reads before it acts and what the reviewer judges the diff against. The testing strategy is where the evidence rules live: every coherent claim gets one construction mode, and unless that mode is preservation, one executed mutation per behaviour, whose four exit codes land in the run log.

What is deterministic, and what is not

Everything a model does varies from run to run. Everything that decides whether the model's work counts does not. The factory is built on that split, with a third tier where a fixed check sits over a free choice.

Deterministic

Same input, same answer, no model involved.

  • The guards: the git hook, the handoff check, the green-before-done gate, pre-commit, pre-push, branch protection.
  • Generated artifacts: each one the Conventions table names is compared with what its source produces, byte for byte.
  • Evidence recording: run-log.mjs writes the real exit code of whatever ran.
  • CI: the suites the testing strategy names, run on the merge result; a merge only when the named checks are green, always a squash by GitHub.
  • The sweep-scope allowlist, applied by a script from main.
  • State: git, the board scripts, the issue a branch closes.

Non-deterministic

A model decides, and would decide a little differently tomorrow.

  • Intake: what grill-me asks, what to-spec writes, how to-issues slices.
  • Work-pick: which card is recommended and why.
  • Planning and routing: the plan, its review, which seat builds.
  • The build: the code, the tests, and which mutation is chosen.
  • Review: the findings, and the decision to fix or dismiss each.
  • Owner-facing prose: the candidate table, the pull request body.
  • The routines: what the sweep repairs, what verdict the triage gives.

The interesting middle

A fixed check over a free choice. The path is never reproducible; the conditions for the work to count are.

  • A model chooses the test and what to break. Red then green, as two recorded exit codes, is not a choice.
  • A model writes the plan. A hook refuses to dispatch it with a field missing.
  • A model writes the source. Bytes decide whether the generated artifact matches it.
  • A model repairs the docs. A script decides whether it stayed inside its allowlist.

A generated artifact, in plain words. Nobody writes a generated artifact by hand. It is derived from its source, the same way every time. When an agent changes the source, it must regenerate the artifact. The risk is that it forgets, edits the generated file directly, or regenerates from an older state, and nobody would notice by reading either file. So the checks the Conventions table in AGENTS.md names compare the committed artifact with what its source produces, byte for byte. Identical, or refused. Whether the source is good is judgment. Whether the committed artifact is exactly what that source produces is a yes-or-no comparison, and it never varies.

What none of this covers: a model being confidently wrong inside the space the guards allow. A plausible plan, a test whose oracle copies the implementation, a review that misses a real defect. The defences there are themselves non-deterministic: the independent-oracle rule, the fresh reviewer, and the owner's two reads of the pull request body.

The standing routines

Where the Conventions table marks the documentation routines active, two scheduled cloud agents keep the documentation true without a human reading it first. Their prompts are one-line bootstraps that name a manual in the repository, so what they do is changed by pull request, never in a console. Neither may edit the manual that constrains it.

Two runtimes, one contract

The factory runs on Claude Code and on Codex and switches between them. AGENTS.md is the contract; CLAUDE.md imports it and adds two Claude-only notes. Skills are written under .agents/skills/ and copied byte for byte into .claude/skills/. Each seat carries the same charter on both runtimes, under .claude/agents/ and .codex/agents/, and the safety hooks exist as twins. On Codex, .codex/agents/*.toml owns model routing and, where the repository supplies a browser rule file, a browser run prompts first.

What transfers beyond this repository

  1. One contract file both runtimes read, with skills for the steps and hooks for what must never happen.
  2. Two human gates, phrased for a reader of prose: what to build, and whether the finished change may ship.
  3. One worktree and one draft pull request per issue; the platform's own auto-merge as the only merge.
  4. Seats with narrow charters, bounded handoffs through a template, and judgment settled in the plan rather than absorbed by the session.
  5. One construction mode per claim and one executed mutation per behaviour, with exit codes recorded by a script.
  6. A fresh review of the final tree, then an external reviewer on the draft, then CI on ready.
  7. A board, git, and documentation as three distinct stores, reconciled rather than assumed consistent.
  8. Evidence limits as visible as evidence successes: missing evidence is unavailable, never a pass.
